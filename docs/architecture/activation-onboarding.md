# Onboarding Step 6 frontend

`/onboarding/activation?merchantId=<id>` renders the final-review screen. It retains session/membership checks and earlier store/LINE gates in the dynamic onboarding route. After a confirmed Step 5 save, the final review also opens when context is the current incomplete step. Review access does not complete context or activation. Both back links return to `/onboarding/context` with the same merchant ID. Step 1–5 prerequisite gates and authoritative progress are unchanged.

`ActivationPage` reuses `OnboardingBranding`, the onboarding font stack, shared `Card`/`Button`, existing mascot/logo assets, existing LINE mark and lucide icons. Four small section components show readiness, active channel, saved AI summary and explicit confirmation. Flex/grid/rem-based CSS follows the 35:37 split and the existing responsive breakpoints; no exported absolute-position canvas or scaling transform is used.

`ActivationViewModel` separates presentation from the authenticated activation-readiness response. `ReadinessStatus` formats the four independent backend checks, `ActiveChannel` shows safe channel metadata, and `AiSummary` formats the saved assistant name/tone/fallback. `MOCK_ACTIVATION_DATA` is removed. Zero optional products/FAQ does not block activation, and aggregate readiness comes exclusively from the backend.

The checkbox starts unchecked. The submit button requires backend `ready === true`, disabled AI, an eligible Owner and confirmation. Submission POSTs an empty command and prevents double clicks. Only a successful response with `success === true` and `aiEnabled === true` leads to `router.replace` of the existing `/dashboard?merchantId=<id>&activation=success` route. Dashboard feedback is displayed only when authenticated membership and current backend onboarding status also confirm completion; the query is a presentation hint, not activation state. Failed POSTs or inconsistent success responses stay on Step 6. A 409 refetches readiness; GET errors show Thai retry without ready rows. Completed Step 6 entry and the existing onboarding entry redirect to Dashboard with merchant context. Successful OAuth callbacks already enter that onboarding route. Staff remains read-only. No browser storage or duplicate completion state is introduced.

At desktop/tablet widths the reused branding panel stays sticky while the right content scrolls natively. The opt-in `fitViewport` branding style adjusts the heading/spacing and contains the whole mascot in remaining viewport space. Other onboarding pages do not opt into this sizing change. Tablet status badges wrap below their text; mobile uses the existing compact branding, full-width cards and stacked actions. Native checkbox, semantic links/button, heading associations, textual status badges, live success feedback and visible focus support keyboard/accessibility.

The [backend implementation](merchant-ai-activation.md) supplies readiness, activation/pause commands and runtime gating. `/dashboard/settings?merchantId=<id>` reads this same state and sends DELETE after explicit pause confirmation. Multi-merchant accounts select from authenticated memberships without a hardcoded default. Step 6 is complete only while AI is enabled.
