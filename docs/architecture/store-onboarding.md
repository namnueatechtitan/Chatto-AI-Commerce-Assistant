# Step 3: store information and catalog imports

This implements the updated Step 3 reference, not the earlier proposal to make
store information a Step 5 substep. `/onboarding/store` is the single creation and
editing page. The existing `/merchants/new` route remains available for additional
stores; it is not a second mandatory onboarding screen.

## Reinspection and database changes

The repository still matched the read-only audit: Merchant lacked store details,
FAQ/product management routes were placeholders, and no upload/job/storage model
existed. Products have name, description, category, brand and status. SKU, price,
currency and stock exist on ProductVariant, not Product. This implementation
imports Product descriptions only; it adds no inventory or commerce behavior.

Merchant adds nullable operatingHours (255), description, phone (50), email (255)
and address. Existing shopName and businessCategory are reused. It also adds
informationRevision (default 0) and a nullable unique onboardingRequestId for
first-creation retries. Existing records retain IDs, memberships, roles and data.

FAQs reuse KnowledgeBaseDocument with `type=faq`, question in title, answer in
content, and ACTIVE/ARCHIVED status. No FAQ table, vector processing, or AI call
is introduced. Unrelated document types are preserved.

CatalogImport persists file metadata, merchant, actor IDs, SHA-256, transient
storage key, status, bounded parsed preview/errors, result counts, confirmation
actor/time, expiration and audit timestamps. Its merchant/hash unique constraint
prevents duplicate jobs. Status values are constrained in the database.

Migration: `20261002000000_store_information_catalog_import/migration.sql`.
Reviewed against `prisma migrate diff` from the original schema: only ADD COLUMN,
CREATE TABLE/INDEX and a foreign key, plus a status CHECK and BEGIN/COMMIT. No
existing table is dropped, reset, truncated or recreated. On 2026-10-02, after the
user explicitly confirmed the target as local development, this migration was
applied to `chatto_phase2` at localhost:5432. All four migrations are applied.
Read-only fingerprints confirm all 42 original records across 28 tables retain
their original column values after deployment and PostgreSQL integration tests.

After confirming the deployment target, from the repository root:

```powershell
pnpm.cmd --filter @chatto/api prisma migrate deploy
pnpm.cmd --filter @chatto/api prisma:generate
```

Restart the API after migration/client generation. Normal Prisma 5.22 client
generation, strict API compilation, both PostgreSQL rollback suites and complete

Shared/production deployment must use the reviewed migration through the normal
deployment process; this task does not apply it to those databases.

## API contract

All routes authenticate the existing opaque session. Reads require active
membership; writes require Owner membership and an ACTIVE/TRIAL merchant. Mutation
requests require the existing exact WEB_URL Origin. UUID parameters are validated.
Responses use no-store and never include credentials, storage paths or tokens.

| Method / route | Responsibility |
| --- | --- |
| GET /onboarding/status?merchantId=UUID | Persisted, sequential six-step progress |
| POST /onboarding/store | Full first-store creation with requestId |
| GET /merchants/:merchantId/information | Store fields, active FAQs, canEdit |
| PATCH /merchants/:merchantId/information | Store and FAQ transaction with revision |
| GET /merchants/:merchantId/catalog-imports | Latest 20 import summaries |
| POST /merchants/:merchantId/catalog-imports | One multipart `file`, returns 202 |
| GET /merchants/:merchantId/catalog-imports/:importId | Status, preview and results |
| POST /merchants/:merchantId/catalog-imports/:importId/confirm | Explicit transactional import |
| POST /merchants/:merchantId/catalog-imports/:importId/cancel | Cancel a non-imported job |
| GET /merchants/:merchantId/catalog-imports/template/:format | Authenticated CSV/XLSX templates |

Creation requires shopName, businessCategory, operatingHours and a UUID requestId.
The client generates one requestId per creation attempt and reuses it for retries.
A user advisory lock serializes first-store creation. The existing
MerchantsService.createWithTransaction creates Merchant and Owner membership;
fields and FAQs are saved in the same transaction. A repeated requestId returns
the original owned result, without overwriting it. A different requestId after a
store appears returns 409 and requires explicit selection.

Updates require the current integer revision. A conditional revision increment
and merchant advisory lock prevent stale overwrite. FAQ changes are in that same
transaction. Provided IDs must belong to this merchant and type=faq; new IDs are
generated by the backend. Duplicate/foreign IDs reject the whole update. FAQ
limits are 50 pairs, question 255 and answer 5,000 characters. Empty lists are
allowed. `faqs=[]` archives only existing FAQs; omitting faqs preserves them.
The HTTP server retains its bounded JSON-body limit (100 KiB).

Optional store fields are replaced by the submitted values; blank values become
null. Store description is capped at 5,000 and address at 2,000 characters.
Business email is independent of the user's OAuth email. Hours are validated as
nonblank, single-line text up to 255 characters (e.g. จ.–ศ. 09:30–18:00). The UI
uses stable category identifiers while retaining an existing custom category.

## Upload and parsing architecture

Session, Origin and owner authorization run before multipart parsing. Multer 2
buffers at most one 5 MiB file, no extra fields, with a 30-second upload timeout.
Each API process reserves at most two simultaneous uploads/parser workers; busy
requests return 503 and can be retried. Extension/MIME must agree; XLSX/PDF also
require signatures, and CSV must be valid UTF-8 without NUL bytes.

Files are written with generated UUID keys to a private directory, never under
Next public assets. User filenames are display-only, with path/control characters
removed. Originals are deleted when parsing ends, fails, or is cancelled; the
database preview is sufficient for confirmation. A cleanup sweep each minute
expires previews after 24 hours, marks interrupted PARSING jobs failed, and removes
abandoned UUID upload files older than two minutes. Metadata/previews remain for
audit. Original files have no public download endpoint.

Workers receive only the private file path and format, with no database/OAuth
credentials or internal tokens. They have a 15-second timeout, 128 MiB V8 old-heap,
16 MiB young-heap and 4 MiB stack limits. File size, ZIP expansion, text and row
limits also bound native/library work; this is not an OS sandbox or a strict total
RSS limit. The compiled worker runs in production; the existing TypeScript runtime
loads source workers in API development mode. No uploaded macros/scripts run.

The service stores PARSING → PREVIEW or FAILED. Confirm/cancel and reupload are
merchant scoped. Failed/cancelled/expired jobs can be reparsed by reuploading the
same bytes. Reuploading an active/imported file reuses its existing job. Confirm
serializes by merchant, imports all valid rows and commits counts/job state in one
transaction. Database failures roll back products and leave a retryable preview
with a persisted error. Repeated confirmation returns the original result.

## Formats and matching

CSV/XLSX columns: `name` (required), `description`, `category`, `brand` (optional).
Recognized Thai headings are ชื่อสินค้า, รายละเอียด, หมวดหมู่ and แบรนด์. Unsupported
columns, including SKU/price/stock, are ignored with a preview warning. Templates
are also provided in `apps/web/public/templates` for a user who has not saved a
store yet. Downloaded CSV cells are quoted and formula prefixes escaped.

CSV supports UTF-8 Thai/BOM, quoted commas and multiline quoted fields. XLSX
requires one visible nonempty sheet. ZIP preflight rejects encryption, macros,
external links, embedded content, unsafe paths and XML DTD/entities; it limits
entries to 300, total expansion to 32 MiB, each entry to 8 MiB, and expansion ratio.
Formula, hyperlink and error cells are rejected rather than executed/evaluated.
Both formats allow at most 500 product rows and 12 columns.

PDF.js extracts text only, with at most 20 pages, 100,000 text characters and
10,000 text items per page. Encrypted documents, JavaScript actions and attachments
are rejected. Only an explicit pipe-delimited table is structured:

```text
name | description | category | brand
Flower bouquet | Fresh flowers | flowers | Chatto
```

Arbitrary prose, layouts without this table and image-only/scanned PDFs do not
produce invented products. OCR is unsupported. Text/table extraction must be
reviewed; other PDF text is ignored. No external AI extraction or paid service is
used. PDF fixtures/fonts remain untrusted input, not prompt instructions.

Matching is merchant-scoped normalized name: Unicode NFKC, trim, collapse
whitespace, then locale-independent lowercase. Duplicate names inside a file
are row errors. A single existing match updates that product while preserving
its ID, status, variants and images. Multiple existing matches are flagged and
must be resolved. Omitted optional columns preserve existing values; blank cells
in provided columns clear those fields. New products are DRAFT and do not
automatically become active AI context or inventory. Valid rows are imported only
after the user confirms; invalid rows are visibly skipped and counted.

## Frontend and readiness

OnboardingBranding is extracted from OnboardingShell and reused unchanged by the
dashboard. Its long-form gradient variant keeps the mascot proportional. Store
InformationForm provides required-field indicators, prefill, revision conflicts,
FAQ add/delete, owner-only controls, loading/errors, and skip/save behavior.
CatalogImport provides select/drop, upload progress, polling, preview/errors,
confirm/cancel, results, retry and reloadable history. The legacy
`/onboarding/store-information` route redirects to the same page. Merchant detail
and completed Step 3 link to the form. Multiple stores require explicit selection.

Uploading before initial creation validates and saves required details plus valid
FAQs on the same page, then uploads against that saved merchant. This is explained
beside the file control. Skip saves valid required/contact data and complete FAQs;
incomplete edits to an existing FAQ retain its previously saved pair. Explicit
FAQ deletions are retained. Missing required fields prevent skip from advancing.

The six steps are account, session, store information, LINE OA, AI context,
activation. Step 3 requires an ACTIVE/TRIAL Merchant, an active Owner membership,
and valid name/category/hours. FAQ/catalog are optional. Legacy minimal merchants
remain incomplete until those details are supplied. Read-only members can see
store readiness but cannot change it. Successful save returns to fresh persisted
onboarding status: 3/6=50%, Step 4 current when later steps are incomplete.
Progress survives refresh and authentication changes; localStorage is not used.

Existing LINE/context checks remain based on persisted channel credentials/flags
and AI settings plus active knowledge/products; they do not perform provider token
verification or fabricate missing configuration. LINE now has a
[frontend-only Step 4 editor](line-onboarding.md); real connection and context
editing remain unavailable. There is no persisted activation contract, so activation stays false.
Imports neither enable LINE webhooks nor add real OpenAI/RAG behavior.

## Configuration and limits

Node 22.13+ is required by the installed PDF.js version (tested on Node 22.14).
`CATALOG_STORAGE_DIR` optionally overrides the API's private `storage/catalog`
directory. The API identity needs private read/write permission there. Local disk
is intended for a single API instance; distributed jobs/object storage and durable
background queues are not implemented. On restart interrupted jobs become
retryable failures rather than silently continuing.

No new external account, OAuth credential or environment secret is needed.
Existing DATABASE_URL and WEB_URL configuration is reused. For reverse proxies,
allow multipart requests up to 5 MiB plus framing and at least a 35-second response
window; retain the application limits. Storage/build artifacts are excluded from
Git and Docker context. See the validation report for executed and pending checks.
